# MANIFESTO

> **Software should explain itself.**

---

# Why DevLens Exists

Software has become one of humanity's most powerful tools.

Yet, understanding software remains surprisingly difficult.

Every day, developers spend hours searching for answers that already exist inside the source code.

The problem is not a lack of information.

The problem is that information is fragmented.

Architecture lives in diagrams.

Documentation lives in Markdown files.

Knowledge lives in senior engineers.

Events live in Kafka.

APIs live in OpenAPI.

Discussions live in Pull Requests.

History lives in Git.

The source code remains the only true source of truth.

DevLens exists to unify that knowledge into a living representation of the software itself.

---

# Our Beliefs

## Software Should Explain Itself

Documentation should never become obsolete.

Architecture should never become outdated.

Every code change should update the system's understanding automatically.

If the code changes, DevLens changes.

---

## Knowledge Is More Valuable Than Code

Writing software becomes easier every year.

Understanding software becomes harder every year.

AI is making software generation cheaper.

Understanding systems is becoming the true competitive advantage.

We build tools for understanding.

Not for generating more code.

---

## AI Is Not The Product

Artificial Intelligence is an interface.

Knowledge is the product.

The Knowledge Graph is the heart of DevLens.

Everything else exists to help people explore it.

---

## Visual Understanding Beats Conversational Understanding

Humans recognize patterns visually.

A graph often explains more than a thousand lines of documentation.

A living architecture communicates faster than any chat conversation.

Conversations are temporary.

Visual models are persistent.

Our default interaction is exploration.

Not conversation.

---

## The Software Is Alive

Software is not static.

Architecture evolves.

Dependencies evolve.

Events evolve.

Documentation evolves.

Understanding should evolve too.

DevLens must always represent the current reality.

Never yesterday's documentation.

---

# Engineering Principles

## Performance Is A Feature

Fast software feels simple.

Slow software feels complicated.

Every interaction should feel immediate.

Every animation should have a purpose.

Every request should justify its existence.

Performance is part of the user experience.

---

## Simplicity Wins

Complex code impresses developers.

Simple code survives years.

We choose simplicity whenever possible.

Every abstraction must justify its existence.

Every pattern must solve a real problem.

Architecture exists to reduce complexity.

Not to create it.

---

## Readability Is More Important Than Cleverness

Code is read more often than it is written.

Future maintainability always outweighs short-term elegance.

The next developer should understand our code without reading documentation first.

---

## Build For The Next Five Years

Temporary shortcuts become permanent systems.

Every architectural decision should consider long-term maintenance.

We optimize for evolution.

Not speed alone.

---

## The Browser Should Render

The Backend Should Think

Heavy computations belong on the server.

The frontend exists to provide an incredible experience.

Not to process large datasets.

Every unnecessary computation performed in the browser is a design failure.

---

## Every Pixel Has A Purpose

Interfaces should communicate.

Not decorate.

Animation exists to explain change.

Color exists to communicate state.

Motion exists to guide attention.

Nothing should exist merely because it looks impressive.

---

# Product Principles

## The Knowledge Graph Is The Source Of Truth

Not documentation.

Not prompts.

Not AI.

The graph.

Everything else derives from it.

---

## Documentation Is A Product

Documentation is not an afterthought.

Documentation is one of our primary deliverables.

It should always be:

accurate

beautiful

searchable

up-to-date

automatically generated

---

## Architecture Is A Product

Architecture is not an internal implementation detail.

It is part of the product experience.

Users should enjoy exploring their systems.

Understanding software should feel intuitive.

---

## Every Feature Must Increase Understanding

Before building a feature, ask:

Does this help developers understand their systems better?

If not, reconsider.

---

## Do One Thing Exceptionally Well

We are not trying to become:

an IDE

a CI/CD platform

a monitoring platform

a cloud provider

a source control system

We build software intelligence.

Everything else is secondary.

---

# User Experience Principles

## Zero Learning Curve

The interface should feel familiar.

Developers should understand the product naturally.

If a tutorial becomes mandatory, we failed.

---

## Instant Feedback

Users should never wonder whether something is happening.

Every long operation provides progress.

Every action provides feedback.

Every interaction feels responsive.

---

## Beautiful Software Increases Productivity

Developers spend thousands of hours inside their tools.

Beautiful software creates trust.

Calm interfaces reduce cognitive load.

Good design is not decoration.

It is functionality.

---

## Less Noise

Every button must justify itself.

Every panel must provide value.

Every screen should communicate a single idea.

White space is a feature.

Silence is a feature.

Focus is a feature.

---

# Technical Principles

## Portability Over Vendor Lock-In

DevLens should run anywhere.

Cloud providers are implementation details.

Docker first.

Kubernetes ready.

No mandatory managed services.

---

## Open Standards

Whenever possible, adopt open standards.

OpenAPI

AsyncAPI

Markdown

Mermaid

PlantUML

OpenTelemetry

Avoid proprietary formats.

---

## Async By Default

Long-running operations should never block users.

Background jobs exist for a reason.

Good software feels immediate.

---

## Observe Everything

Every important event should be measurable.

Every failure should be traceable.

Every decision should be explainable.

If something cannot be observed, it cannot be improved.

---

# Architecture Principles

## Modules Own Their Domains

Every module owns its business rules.

Boundaries should be explicit.

Coupling should be minimized.

Communication should be intentional.

---

## DDD Should Be Practical

Architecture exists to simplify.

Not to impress.

Avoid academic implementations.

Prefer understandable code.

Prefer explicit flows.

Prefer small domains.

---

## Events Must Have Meaning

Kafka is not a design pattern.

Events represent business facts.

If an event does not communicate a meaningful business occurrence, it probably should not exist.

---

## AI Should Reduce Cognitive Load

AI should never replace understanding.

It should accelerate understanding.

The goal is confidence.

Not automation.

---

# What Success Looks Like

DevLens succeeds when:

A new engineer understands a complex system in fifteen minutes.

Documentation never needs manual updates.

Architecture reflects reality.

Developers trust the platform.

Teams stop asking repetitive architectural questions.

Knowledge survives employee turnover.

Software becomes easier to evolve.

---

We will never optimize for hype over usefulness.

We will never sacrifice maintainability for unnecessary complexity.

We will never introduce technology simply because it is fashionable.

We will build software that we genuinely want to use every day.

Living.
